Chapter 6: The Training Toolkit

Learning Objectives

  • State the question each tool answers: step size (learning rate), remembered direction (momentum), cost per step (minibatches), a rate per parameter (Adam)
  • Explain why a single learning rate cannot suit a valley-shaped loss surface
  • Choose between the tools: which to reach for, when, and what each can get wrong
  • Race the tools against each other on a real network, and know what the toolkit cannot do

Motivation

  • Every training run in this series so far used plain gradient descent with a learning rate of 0.25, and we never said why. This chapter explains it: where the number comes from, what happens when it is wrong, and what the standard improvements do.
  • Nothing about the networks changes. The toolkit is entirely about how we descend, not what we descend on. And each tool in it is the answer to one specific question that plain gradient descent answers badly:
    1. How big should a step be? (the learning rate, and its cliff)
    2. Can the path remember the direction it was already going? (momentum)
    3. Does every step need to look at all the data? (minibatches)
    4. Can each parameter have its own step size? (Adam)
  • The test track for everything: chapter 2's exact data and network (three sigmoid blocks, 80 noisy points, loss of the generating parameters 0.0449). Every experiment runs right here in the page.

1. The Learning Rate You Never Chose

  • Recall the update: every parameter moves against its gradient, and the learning rate $\alpha$ scales the move: $w \leftarrow w - \alpha \, \nabla \mathcal{L}$.
  • In the panel below, pick a learning rate and press run. Each run adds one loss curve to the plot (the epoch axis is logarithmic, and the dashed line is the loss of the generating parameters). Then change the rate and run again. Try 0.01, then 0.25, then 2, then 4.
  • What you should find on this network:
    • $\alpha = 0.01$: reaches the dashed line after roughly 5,000 epochs. Nothing wrong, just slow: each step is tiny, so it takes many.
    • $\alpha = 0.25$ (the series default): about 200 epochs. Comfortable.
    • $\alpha = 2$: about 26 epochs. Our default was more careful than it needed to be, on this loss surface.
    • $\alpha = 4$: the loss explodes. Each step overshoots so badly that the next gradient is bigger than the last, and the run leaves the plot within a few epochs. This is the cliff, and everyone who trains models learns to respect it.
  • So the learning rate is a trade with a hard edge: the fastest safe rate sits just below the cliff, and the cliff's location depends on the loss surface, which is why there is no universal right number.

2. The Valley: Why One Rate Cannot Fit Every Direction

  • Why does the cliff exist, and why is the best rate so hard to pick? Because a loss surface is rarely a round bowl. It is usually a valley: steep across, nearly flat along. Chapter 2's surface is like this too; some parameters (the slopes $w_j$) bend the loss sharply, others (the heights $v_j$) barely.
  • The panel below shows a two-parameter valley with its loss drawn as contour lines, and the path gradient descent takes from the starting point. Keep momentum at 0 for now and play with the learning rate:
    • the gradient mostly points at the nearest steep wall, not along the valley floor, so the path zig-zags from wall to wall while creeping toward the minimum;
    • raise the rate and the zig-zag widens until the path bounces out entirely: the steep direction sets the cliff;
    • lower it and the bouncing calms, but progress along the valley crawls: the flat direction pays the price.
  • That is the trap: one number must serve both directions, and the two directions want different numbers.

3. Momentum: Remember the Direction You Were Going

  • Look at the zig-zag path again and ask: what information is gradient descent throwing away? Its own recent past. Step after step, the across-the-valley part of the gradient flips sign, while the along-the-valley part points the same way every time. Any method that remembered the last few steps could notice this: the flipping parts would average out, the steady part would add up.
  • That method is momentum. Keep a running velocity $z$: each step, fold the new gradient into the velocity, then move along the velocity:
$$z \leftarrow \beta z + \nabla \mathcal{L}, \qquad w \leftarrow w - \alpha z$$
  • $\beta$ is how much of the old velocity survives each step ($\beta = 0$ is plain gradient descent). Now look at the valley again and raise $\beta$ toward 0.9:
    • the wall-to-wall components of the gradient keep flipping sign, so inside the running velocity they cancel themselves out: the zig-zag fades;
    • the along-the-valley component always points the same way, so it accumulates: the crawl becomes a roll;
    • push $\beta$ to 0.99 and the ball has too much memory: it overshoots the minimum and swings back and forth for a long while.
  • So when does momentum help, and when does it hurt?
    • Helps whenever the surface is a valley, which is nearly always: the deeper and narrower the valley, the bigger the win. It also lets you use learning rates that would explode without it (try $\alpha = 0.03$ with $\beta = 0$, then with $\beta = 0.8$): the memory smooths the bouncing that causes the explosion.
    • Hurts when $\beta$ is too high for the surface: the ball overshoots and swings, and the swinging can be slower than the crawl it replaced. $\beta$ is one more number to get right; 0.9 is the standard default because it behaves well on most surfaces, not because it is always best.
  • You will race momentum against plain gradient descent on the real network in section 6. From our own runs: $\beta = 0.9$ at $\alpha = 0.25$ reaches the dashed line about eight times faster.

4. Minibatches: Does Every Step Need All the Data?

  • A different question now, about cost. Every step so far computed the gradient using all 80 points. With 80 points that is nothing; with eighty million it would be everything: one single step would mean a full pass over the dataset, and training takes thousands of steps.
  • The observation that saves deep learning: a small random sample of points gives a rough estimate of the same gradient at a fraction of the work. The average direction over 8 random points is not the true gradient, but it points roughly the right way, and it costs a tenth as much. Training on such samples is called minibatch training (the whole approach: stochastic gradient descent).
  • The fair comparison is per unit of work: one pass through the data buys either one exact 80-point step or ten rough 8-point steps. Which is worth more? On this network, the ten rough steps, by a wide margin: they reach the dashed line in about a tenth of the passes. Cheap approximate steps, taken often, beat expensive exact steps taken rarely.
  • The price is noise: a minibatch loss curve wobbles on the way down, because every step follows a rough estimate. You will see the wobble in section 6.
  • When is full batch the right call? When the dataset is small enough to afford it, which is exactly why this series could use it for six chapters. Almost no real dataset is.

5. Adam: a Step Size for Every Parameter

  • Momentum fixed the zig-zag, but one thing about the valley is still unsolved. The whole problem was that different directions want different learning rates, and momentum still uses a single $\alpha$ for every parameter. Can each parameter have its own?
  • That is Adam's question, and its answer is to learn the rates from the gradients themselves. For each parameter, Adam keeps two running averages:
    • the average gradient $m$: which way this parameter has been pushed lately (this is momentum's velocity, under a different name);
    • the average squared gradient $s$: how big this parameter's pushes tend to be, a measure of how steep its direction is.
  • Each parameter then steps by the direction over the typical size:
$$w \leftarrow w - \alpha \, \frac{m}{\sqrt{s}}$$
  • Read the division as a correction: a parameter with big gradients (a steep direction) gets its steps shrunk, one with small gradients (a flat direction) gets its steps boosted. The valley is reshaped into something much closer to a round bowl, one parameter at a time, and the round bowl is the one surface where a single $\alpha$ was always fine.
  • So when Adam, and when momentum?
    • Adam is the convenient default of modern practice: it usually works at its standard settings with no tuning, which matters when a training run costs hours. Note its $\alpha$ has a different meaning (the division changes the scale), so its defaults are small numbers like 0.01.
    • Momentum is the simpler machine (one running average where Adam keeps two), and on some problems a carefully tuned momentum run ends at a slightly better answer than Adam. When the last bit of quality matters, people tune both and race them.
    • Neither is free: Adam keeps two extra numbers per parameter, momentum one. For our 10-parameter network that is nothing; for a billion-parameter model it is real memory.

6. The Race

  • Now that all the runners have been introduced, race them yourself. Everything runs on chapter 2's data and network; each run adds a labeled loss curve. A course worth running, in order:
    1. gradient descent, $\alpha = 0.25$, all 80 points (the series default: the one to beat);
    2. momentum, $\alpha = 0.25$ (the zig-zag cancelled: about eight times faster);
    3. Adam, $\alpha = 0.05$ (the reshaped bowl);
    4. gradient descent, $\alpha = 0.25$, batch of 8 (watch the wobble, and where it lands per pass);
    5. gradient descent, $\alpha = 4$ (over the cliff, so you know what it looks like).
  • Note where every successful run ends: on the same dashed line. The toolkit changes how fast you descend, not where you arrive; keep that in mind for section 8.

7. Which One Should You Use?

  • The practical rules most people follow, and why:
    • Minibatches: always, on real data. Training on the full batch is something only a tiny teaching dataset like this one allows.
    • Adam at its defaults first. It is the first tool to reach for because it usually just works, and your time matters more than a small speed difference.
    • Momentum when you can afford to tune, or when Adam's two extra numbers per parameter are too much memory, or when a tuned run's final quality matters more than convenience.
    • Plain gradient descent mostly for understanding, which is what this series used it for: every idea in chapters 1 to 5 was visible without the toolkit in the way.
  • And whichever you choose, the learning rate is still the number to check first when a run explodes or crawls. The tools reshape the problem; they do not remove it.

8. What the Toolkit Cannot Do

  • One more experiment, and it matters. Recall chapter 3's deep network with the small starting weights, the one that gets stuck at a loss of about 0.15 while the recipe sits at 0.047. Can the toolkit save it?
    • plain gradient descent, 400,000 epochs: stuck at 0.154;
    • momentum, $\beta = 0.9$: stuck at 0.153;
    • Adam: stuck at 0.153.
  • It cannot. That network is not moving down slowly, it is moving down to the wrong place: from that starting point, every downhill path leads to the same poor answer, and a faster method just gets there faster.
  • The lesson, worth keeping: the toolkit makes descent faster, not wiser. Where the descent ends up is decided by the loss surface and the starting point, and fixing those needs different ideas (better starting weights, and layers that keep gradients healthy). Those ideas get their turn when the networks grow deeper.

(Optional) The Toolkit in Code

Momentum in numpy is two lines more than gradient descent (one velocity per parameter array; here for chapter 2's network):

lr, beta = 0.25, 0.9
zw = np.zeros_like(w); zb = np.zeros_like(b); zv = np.zeros_like(v)

for epoch in range(20_000):
    gw, gb, gv = gradients(w, b, v, x, y)     # as in chapter 2
    zw = beta*zw + gw;  w -= lr*zw
    zb = beta*zb + gb;  b -= lr*zb
    zv = beta*zv + gv;  v -= lr*zv

Minibatch training shuffles the points each pass and steps on each slice:

B = 8
for epoch in range(2_000):
    order = np.random.permutation(len(x))
    for i in range(0, len(x), B):
        batch = order[i:i+B]
        gw, gb, gv = gradients(w, b, v, x[batch], y[batch])
        w -= lr*gw;  b -= lr*gb;  v -= lr*gv

In PyTorch, the toolkit is one argument:

optimizer = torch.optim.SGD(model.parameters(), lr=0.25)                 # plain
optimizer = torch.optim.SGD(model.parameters(), lr=0.25, momentum=0.9)   # momentum
optimizer = torch.optim.Adam(model.parameters(), lr=0.01)                # Adam

Chapter Highlights

  1. The learning rate is a trade with a cliff: too small crawls, too big explodes, and the cliff's location depends on the loss surface.
  2. Loss surfaces are valleys: steep across, flat along. One rate cannot serve both directions, and that problem is what the rest of the toolkit goes after.
  3. Momentum keeps a running velocity: zig-zag components cancel, along-the-valley components accumulate. Eight times faster on our own chapter 2 network.
  4. Minibatches buy many cheap noisy steps for the price of one exact step, and win per pass through the data. Real training is minibatch training.
  5. Adam gives each parameter its own step size from the gradient's history, flattening the valley one direction at a time.
  6. The toolkit makes descent faster, not wiser: chapter 3's stuck network stays stuck. Where you start from, and the shape of the surface, are different problems.
